```markdown
# Synapse Router — Cursor Rules

You are an expert Synapse Router developer working on a TypeScript monorepo.

## Project Identity

[Brief: what Synapse Router is, core philosophy "开发时协商运行时无感"]

## Communication Rules

- Always communicate with users in 简体中文
- Always write code comments, docstrings, and log messages in English
- Always use English for all identifiers (variables, functions, types)

## Architecture Rules

- Always define Schema contract before making provider calls (contract-first)
- Always use Connector only for HTTP + field mapping + base_url override (thin layer)
- Never auto-update Schema Locks when packs change (immutable)
- Never import @synapse-router/* in generated SDK code (zero-dependency)
- Always use createBillingConnector() to wrap connectors, never modify internals (wrapper pattern)
- Never write API keys in plaintext (AES-256-GCM vault)
- Always redact API keys in traces/spans

## Code Conventions

- Always use TypeScript strict mode
- Always use Node.js native test runner (tsx --test), not Vitest/Jest (except observability package)
- Always place test files co-located with source: src/*.test.ts
- Always export public API through src/index.ts barrel file
- Always use structured error types, never swallow exceptions
- Always use @synapse-router/observability Tracer, never console.log
- Always use ESM (type: module in package.json)
- Always write commit messages in Chinese, format: <type>: <description>

## Package Structure

[Package naming and organization patterns:
- @synapse-router/<name> npm scope
- apps/ for application entry points
- packs/ for Provider Packs
- Each package: independent tsconfig.json, build/test scripts]

## File Patterns

[Common file patterns and purposes:
- src/index.ts: Barrel exports (public API)
- src/*.test.ts: Co-located tests
- provider-card.json: Provider capability declaration
- src/commands/<name>.ts: CLI command modules]

## CLI Development

- Always prioritize command-line interface over interactive mode
- Always support --format json|table for output
- Always include complete examples in --help text
- Always validate flags against union types before use

## Testing Rules

- Always write tests for new business logic
- Always mock external services (no real API calls in tests)
- Always use descriptive test names: "should <expected> when <condition>"
- Always clean up temporary files/directories after tests
```
